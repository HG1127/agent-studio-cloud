# 最终成果可靠投递

投递与业务执行分别记状态：`completed` 只代表流程完成，只有投递状态 `delivered` 才代表接收方明确确认。本功能不提供开放公网任务入口，也不替代部署访问保护。

## 选择接收方

在既有 `POST /api/runs` 正文中可选增加 `delivery: { "targetId": "crm.result" }`。接收方只能选择服务端别名，不接受回调网址、请求头、凭据、工作区或执行快照。共享契约位于 `src/contracts/run-delivery-config.ts` 与 `src/contracts/run-delivery.ts`。

任务与投递意图在同一事务创建；原请求重试不能添加、删除或改换接收方，不会创建第二条投递。冻结运行版本与输入规则不变。接收方后来停用时，原任务仍可找回，但投递明确停止，不静默改投其他地址。

## 服务端接收方配置

`RUN_DELIVERY_TARGETS_JSON` 是服务端专用配置；真实地址、请求头和防重保证需要人工确认。例：

```json
[{ "id": "crm.result", "revision": "1", "endpoint": "https://receiver.example.com/results", "idempotent": true, "retentionMs": 86400000, "headers": { "Authorization": "Bearer <密钥>" } }]
```

生产只接受 HTTPS、不带地址内用户名密码或片段的端点；不跟随重定向。本机 HTTP 回环地址仅用于隔离测试。配置最多 50 项，不允许重复别名、危险请求头或无明确防重保证。接收方须按同一防重键原子处理并发与重试，并返回相同回执；不能只声明支持而忽略防重键。有效期为 5 分钟至 1 年。

冻结别名、地址、语义版本、有效期及除 Authorization 外的请求头。原接收账号的 Authorization 凭据可以轮换；改变账号、业务语义或路由必须改变 revision，原投递随之停止，不能借轮换偷偷改换接收方。其他配置改变会停止原投递并要求核对。地址和凭据不返回前端、不写入投递快照。

## 投递与确认

后台在任务成功、失败或取消后冻结快照；不会发送排队、运行中或等待人工处理的中间成果。失败和取消只发送明确终态与脱敏原因，结果为 null。成功结果遵守既有 2MB、32 层 JSON 契约，保留零值、否定值与业务邮箱，对象凭据隐藏后发送。无效或超限成果停止投递，不截断后伪报完整。

POST 正文：`{ "schemaVersion": 1, "deliveryId": "…", "task": { ... } }`。task 沿用 `RunTaskResultView`，只含终态、最终结果、输出契约和本地入口，不含输入、完整上下文、模型或工具凭据、引擎句柄。整个信封最大 2MB 加 128KB；入口链接是原部署内的相对路径。

请求头包含 `Idempotency-Key: delivery:<deliveryId>` 与 `X-Agent-Studio-Delivery-Id`。重试始终沿用同一标识和同一冻结正文。只有 HTTP 200/201 且返回严格 JSON `{ "ok": true, "deliveryId": "原投递标识", "receiptId": "可选回执" }` 才算交付。回执最大 4KB；空正文、错误标识、ok 为 false 或未知字段不算成功。HTTP 202 只表示尚未明确确认，不算已交付。

连接或响应丢失、202、408、425、429 和 5xx 有界重试；其他拒绝或无效回执停止自动发送，等待人工核对。默认最多发送 5 次，退避为 5、10、20、40、60 秒，单次超时 30 秒。首次发送领取时冻结防重截止时间，所有重试和补投不得延长。到期后不再发送。投递是接收方防重保障下的至少一次协议，不声称任何外部系统都能严格只执行一次。

## 持久化与恢复

投递意图、快照、尝试次数、截止时间、租约、回执与人工记录保存在 `run_deliveries`。工作流步骤完成 I/O，编排交给持久 Workflow SDK；瞬时失败抛 RetryableError，永久拒绝抛 FatalError。调度使用原子行锁和租约，不持有数据库事务等待网络。

`GET` 或 `POST /api/deliveries/tick` 必须携带既有 `Authorization: Bearer <CRON_SECRET>`。一次最多冻结 10 个终态任务、领取 10 个待投递或过期租约任务。启动响应丢失保留两分钟租约；后续调度可接管。旧租约迟到的回执不能覆盖新的状态。`claimed` 表示持久领取，不代表已送达。

此入口须由现有外部定时服务按分钟调用；尚未自动加入生产调度，不改动另一分支维护的定时任务配置。没有调用时，已登记意图会保留，但不会冒充已交付。投递失败不会改写成功业务任务的状态，也不会重新运行模型或业务工具。

## 查询与人工补投

`GET /api/runs/<runId>/delivery` 返回 `{ "ok": true, "runId": "…", "delivery": { ... } }`；未选择接收方返回 delivery 为 null，不存在或不可访问返回 404。摘要不读取或返回快照、地址、请求头、防重哈希、租约和引擎句柄。任务回执的可选 `links.delivery` 指向此入口，旧回执兼容。

状态为 waiting_result（等任务结束）、pending（待调度）、queued（已领取或等待重试）、sending（正在发送）、delivered（已确认）、failed（已停止）。状态查询不触发发送，所有响应禁止缓存。

`POST` 同一入口可登记补投，要求同源 JSON、最大 4KB：`{ "requestId": "新 UUID", "confirmed": true, "reason": "已核对接收方实际状态" }`。仅已停止且成果完整的投递允许补投；成功的、处理中的或有效期已过的投递拒绝。每次登记增加 5 次尝试额度，不清零既有次数，不改正文、标识、接收方或截止时间；最多 20 次人工登记。

原 requestId 与规范化原因安全重试只登记一次，不更改历史记录；不同原因返回 409。成功 recorded 只表示登记，不表示已经交付。未知存储结果返回 503、retryable 与 Retry-After: 2，沿用原请求重试。补投动作本身不进行外部 HTTP 调用。

需要先应用追加迁移 `0027_durable-run-deliveries.sql`。真实接收方、生产迁移与分钟调度仍须人工配置；隔离假服务验收不替代真实业务接收系统的防重和副作用验收。
