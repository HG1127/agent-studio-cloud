# V5.7 前端迁移：后端接口缺口

本文件只记录前端按 V5.7 产品信息架构落地时发现的服务端缺口。当前实现没有用静态假数据替代这些能力；已有入口只展示真实查询结果，或明确引导到已有功能页。

## 1. 工作区身份与成员

旧版包含工作区切换、成员列表和角色提示，云端版目前只有固定的演示工作区常量。

- 需要：当前会话查询，返回 `workspaceId`、工作区名称、当前用户显示名与角色。
- 需要：用户可访问工作区列表与切换动作。
- 需要：工作区成员分页查询；后续登录接入时由 Auth.js 会话决定权限。
- 前端契约建议：`WorkspaceSession`、`WorkspaceSummary`、`WorkspaceMemberSummary`，统一放在 `src/contracts/`。

## 2. 全局验收概览

现有验收查询必须传单个助手编号。验收中心为了只展示真实数据，当前会对可见助手并行查询样例与最近验收记录；助手较多时会形成 N+1 查询。

- 需要：按工作区分页返回助手验收摘要的 query。
- 最小字段：助手编号、名称、在用样例数、最近验收状态、通过数、失败数、开始与结束时间、候选版本号。
- 筛选：`status`、`query`、`limit`、`offset`。

## 3. 全局发布概览

现有版本和自动验收查询必须传单个助手编号。发布中心当前对可见助手并行查询版本列表，并对有候选版本的助手读取最近一次验收记录；助手较多时仍会形成 N+1 查询。

- 需要：按工作区分页返回发布摘要的 query。
- 最小字段：助手编号、名称、正式版本、候选版本、历史稳定版本数、最近发布时间。
- 最近验收应明确关联版本编号及完成状态，避免把旧版结果用于新候选；正式版本的真实发布时间也应由服务端返回，不能拿版本创建时间替代。
- 可选：将已有发布门槛结果汇总为阻塞原因数组，避免前端拼装不同查询。

## 4. 应用、业务系统与设备连接

云端后端目前具备模型连接和知识资料，不具备旧版“资料与应用”中的办公应用、业务系统和设备连接管理。环境变量可提供服务端工具注册清单，“资料与应用”页可只读查看名称、用途和风险级别，画布可据此选择工具；这不是可由员工管理的工作区连接实例，也没有持久的连通测试或健康状态。页面明确标明“已登记”不等于“连接可用”，不会将工具端点、动作定义或输入输出结构传给目录组件。画布总览只区分当前清单中的已选择工具、演示工具、未绑定与失效绑定，不宣称已选择的工具已通过执行校验。

- 需要：连接目录、工作区连接实例、连接测试、启停与影响面查询。
- 需要：连接可暴露的工具列表、权限范围和健康状态。
- 需要：助手版本与连接/工具绑定关系的查询与写动作。
- 所有密钥只允许服务端加密保存；前端只能读取掩码与最后测试结果。

## 5. 运行治理与生产事件

旧版包含失败策略、质量抽查、安全规则、生产事件和助手健康度，云端版目前只有运行记录、审批、取消、重试与系统健康检查。`/harness` 已能从真实运行查询展示最近任务、已保存步骤和脱敏轨迹，并从任务详情直达对应诊断；其中的警告/错误只是轨迹级别，不代表规则命中或 Harness 判决。

- 需要：工作区默认运行策略读取/更新动作，契约明确恢复策略、结果复核方式、长期经验上限、抽查比例和上下文预算，并返回修订号；改动只对新运行生效的部分须由服务端明确标注。
- 需要：安全规则分页查询、创建/更新/停用动作及规则命中记录查询。规则优先级和多条命中时的决策必须由服务端解释；前端不能用本地筛选结果冒充实际执行拦截。
- 需要：按运行编号返回计划、上下文来源、预算用量、各治理层决策和质量评估证据的诊断 query；现有运行步骤与追踪只覆盖一部分，不能据此重建旧版 Harness 的完整因果链。
- 需要：只读策略模拟 action，输入已保存的运行快照与模拟身份/环境，返回服务端规则决策及差异；必须明确不会重跑任务或调用外部工具。
- 需要：助手维度的成功率、人工介入率、耗时分位数与失败分类查询。
- 需要：生产事件列表、分派、状态流转、恢复和复盘动作。
- 需要：安全规则列表、启停与命中记录查询。

## 6. 全局搜索与通知

旧版顶部栏包含跨助手、运行和资料的搜索与任务提醒；云端版当前只能通过各页面筛选，提醒入口只能跳到等待确认的运行列表。

- 需要：受工作区和权限约束的全局搜索 query，返回带类型的结果与目标链接。
- 需要：待办摘要 query，至少汇总等待确认、等待继续、失败运行和解析失败资料。
- 如需实时角标，可复用现有 SSE 基础设施增加工作区级摘要事件，不能由前端轮询冒充实时通知。

## 7. 发布门槛、渐进发布与组织治理

旧版发布工作台把候选版本、验收结果、工具授权、运行预算、审批策略和渐进发布放在同一条发布链路中。云端版目前只具备不可变版本、正式版本恢复和逐样例自动验收，因此新版工作台只展示这些真实能力，没有把“灰度中”“预算已配置”或“双人批准”写成可用状态。

- 需要：助手候选版本的发布门槛汇总 query，至少返回候选版本编号、流程快照是否存在、在用样例数、最近验收状态、阻塞原因和允许发布标记。建议契约为 `AgentReleaseGateSummary`。
- 需要：渐进发布策略与实例契约，至少包含阶段比例、每阶段最小运行数、最大失败率、最大人工拒绝率、当前阶段、真实运行指标、最近决定与状态。建议契约为 `ReleaseRolloutPolicy`、`ReleaseRolloutSummary`。
- 需要：开始渐进发布、立即巡检、暂停、继续和回退 Server Action；晋级与回退判断必须在服务端执行并留下操作记录，前端不能按本地计数自行切换状态。
- 需要：工作区运行预算 query/update action，至少覆盖月度运行量、成本单位、单次运行上限、每日工具调用上限、当前用量与自动暂停状态。建议契约为 `WorkspaceRunBudget`。
- 需要：审批策略 query/upsert action，明确动作范围、风险级别、可批准角色、最少批准人数和启用状态。多人人工批准必须继续沿用 Workflow Hook 的暂停/恢复机制，不能由前端模拟票数。
- 需要：发布决策与自动回退事件查询，使发布中心能够解释“谁或什么规则在何时把哪个版本推进、暂停或回退”，并链接到对应运行证据。
- 需要：人工恢复历史版本时提交所见正式版本的预期编号和客户端请求标识，并能按标识精确核对结果。现有动作会校验来源、资源与发布条件并识别部分重复，但若确认后正式版本已被其他人更改，前端无法阻止旧确认覆盖新状态；总览页因此只提供直达版本历史的入口，不直接执行恢复。

## 8. 运行中心状态汇总

现有运行列表 query 支持状态、发起方式和助手筛选，但只返回当前分页记录，无法准确展示旧版任务中心的全量“等你处理 / 正在执行 / 需要处理 / 已有结果”数量。新版运行中心因此只提供真实状态入口，没有用当前页数量冒充工作区总数。

- 需要：按工作区返回运行状态汇总的 query，并与运行列表使用同一权限边界和筛选口径。
- 最小字段：各运行状态数量、总运行数、统计生成时间；可选接受 `agentId` 与 `sourceType` 条件。
- 建议契约：`RunStatusSummary`，至少包含 `queued`、`running`、`waitingApproval`、`waitingEvent`、`completed`、`failed`、`cancelled`。
- 汇总查询应由数据库聚合完成，前端不能通过拉取前 100 条记录推算或声称为全量数据。
- 旧版任务中心支持按任务或助手搜索。需要跨完整运行记录的服务端搜索 query，明确可展示、已脱敏的任务标题来源，并按工作区权限、归档助手、状态和发起方式组合筛选及分页；不能只过滤当前 25 条列表来冒充全量搜索。

## 9. 定时任务管理与精确运行历史

现有后端支持创建、暂停、恢复和归档定时任务，也能按“定时发起”筛选运行记录；但旧版 V5.7 的计划命名、编辑、立即运行和单计划历史仍缺少契约与服务端动作。新版界面没有用前端状态模拟这些能力。创建结果不确定时，前端目前只保留不含运行输入的本标签页核对线索并锁住再次提交；手工核对仍无法替代精确接口。

- 需要：统一定时任务的版本语义。`createScheduleAction` 保存 `schedule.versionId`，恢复动作按该版本是否仍为正式版本校验；但 `api/schedules/tick` 调用 `startRunCore` 时未传 `versionId`，实际运行会选择执行时的当前正式版本。若产品要求旧版的固定版本，应让调度入口传入已保存的版本编号，并在详情 query 返回绑定版本、实际运行版本及变更后的可运行状态；若决定跟随最新正式版本，则需修改恢复校验和契约，明确输入契约变化时的处理方式。在统一前，前端不承诺“固定使用 Vx”。
- 需要：在不改变既有运行证据的前提下，更新执行频率与运行输入的 Server Action；建议使用乐观锁或 `updatedAt` 防止覆盖并发修改。
- 需要：单次“立即运行”动作，必须复用计划绑定的正式版本和输入，并在运行记录中保留对应的 `scheduleId` 与手动触发人。
- 需要：定时任务详情与运行历史 query，按 `scheduleId` 返回最近运行、成功/失败状态、开始结束时间和运行详情链接；当前只能诚实地跳到同一助手的全部自动运行记录。
- 需要：若产品继续保留可读名称和独立时区，需扩展定时任务契约及迁移，至少包含 `name`、IANA `timezone`；在完成数据库迁移前，前端只使用助手名称和固定北京时间。
- 可选：返回 `lastRunAt`、`lastRunId` 和最近一次结果摘要，减少列表页额外查询，并与下一次执行时间使用同一调度口径。
- 需要：创建动作支持客户端生成的幂等请求标识并返回计划编号；网络在写入后断开时，前端才能安全核对或重试，避免同一计划被创建两次。

## 10. 长期经验的人工治理

旧版成长中心支持逐条确认、修正、启停、期限、类别、共享范围与撤销；云端版现有 `MemoryView` 只提供内容、来源运行和归档状态，写动作只有归档/恢复。当前前端只展示真实保存内容、来源和停用/恢复，不将旧版治理标签伪装为已启用。

- 需要：经验详情契约返回修订号、复核状态、可用状态、类别、使用范围、有效期、撤销时间、最后更新人与时间，以及来源助手或团队信息；所有字段必须与真实检索行为一致。
- 需要：确认、修正内容、修改类别或期限、启停与撤销的 Server Action。写入使用修订号防止覆盖并发修改，留下操作记录；修正后的内容需重新经过敏感信息校验。
- 需要：按状态、范围、类别和复核状态分页筛选及工作区级聚合计数；不能用当前页记录推算旧版“全部/正在使用/待核对”的全量数量。
- 需要：服务端定义团队共享经验的授权与检索边界；在此之前前端不提供“团队共享”开关，也不声称经验会跨助手使用。

## 11. 创建助手时的分步澄清与方案预览

旧版 V5.7 的简洁创建流程会先解释工作目标，逐项询问影响执行的缺失信息，展示交付预览与实际业务路径，再由用户确认保存并试用。云端版现有 `createAgentAction` 只接受名称和完整目标文字，一次性创建草稿；目前前端用可选业务蓝图字段改善输入，但不能把静态提问或本地推测冒充服务端已经确认的设计方案。

- 需要：解释目标的 query/action，输入目标文字、已确认回答、已选资料/工具和可选会话修订号；返回服务端校验过的目标摘要、触发条件、输入与交付契约、需要澄清的问题及可预览的流程草稿。建议契约为 `AgentDesignInterpretInput`、`AgentDesignPlan` 和 `AgentDesignQuestion`。
- 需要：按问题提交回答并更新方案的动作，带会话修订号或等效并发控制；旧方案失效时返回可恢复的冲突状态，避免用户回答被覆盖。
- 需要：方案确认并创建助手的幂等动作，绑定经过确认的方案版本，返回助手编号与待试用状态；保存前不得暗中发布或安排自动运行。
- 需要：若产品继续支持跨设备草稿，提供设计会话读取/保存/放弃接口与过期时间；当前仅有本标签页临时恢复，界面不能声称已保存到工作区。
- 需要：若延续旧版“独立助手 / AI 团队”分类，在助手创建、详情和列表契约中明确持久的类型与团队成员关系及筛选口径；现有 `AgentSummary` 没有类型字段，不能从流程节点或名称推断分组。

## 12. 模型连接的持久验证状态与默认连接门槛

旧版 V5.7 在连接列表展示最近测试状态与时间，设为默认连接前要求完成真实服务测试。云端现有 `ModelConnectionView` 仅返回名称、地址、密钥末尾提示、模型列表和默认标记；测试动作只请求列表中的第一个模型并返回当次结果，刷新后没有可核对的验证证据。保存动作目前也不要求先测试即可设为默认。新版前端因此明确写出被测的首个模型，只反馈当前会话的测试结果，不展示持久“已验证”徽标，也不把保存成功或设为默认说成连接可用。

- 需要：服务端持久保存最近测试时间、结果、测试的模型以及脱敏后的失败原因；连接列表 query 返回这些字段，并区分“未测试”“最近成功”“最近失败”和“凭据或地址修改后待重测”。建议在 `src/contracts/` 扩展 `ModelConnectionView`，不能仅依赖浏览器状态。
- 需要：保存/测试动作关联配置修订号，测试结果返回服务端实际使用的模型名称；地址、密钥或模型列表变化后，旧测试结果不得继续作为当前配置的成功证据，也不能用过期页面上的首个模型名称冒充实际被测对象。
- 需要：允许选择连接中的具体模型进行测试，并按模型返回验证结果；仅测试第一个模型不足以证明其余模型可用。
- 需要：由服务端约束设为默认及发布时所选连接的有效性，并返回可操作的阻塞原因；前端校验只能改善体验，不能代替写入门槛。

## 13. 操作记录的对象定位与拒绝证据

旧版 V5.7 的治理审计区分操作人、对象、动作和拦截结果。云端现有操作记录只保存成功写入的关键事件；`targetId` 对流程、版本和验收分别是它们自身的编号，不能直接拼成助手详情路径。新版界面只对助手和运行提供明确详情链接，其他事件仅返回对应列表或中心，不声称已定位到具体对象。

- 需要：审计列表 query 返回可导航的对象摘要与已校验目标路由，至少包含关联助手编号、对象名称、是否已停用/归档，以及对象目前是否仍可访问；跨工作区与权限校验必须在服务端执行。
- 需要：资料、经验、版本和验收的按对象编号定位查询或可分页定位入口，支持从历史操作记录直接找到对应对象，包括已归档对象；不能依赖解析审计摘要文字或拉取第一页碰运气。
- 需要：若延续旧版“正常通行/拦截”审计，增加明确的决策结果、拒绝原因类别、策略编号和发生时间，并记录被服务端拒绝的动作；现有成功写入记录不能被前端当作完整安全审计。

## 14. 交付报告的人工修订与正式验收

旧版 V5.7 结果页允许员工修订最终交付中的文字字段，再对具体修订版进行人工验收，并导出业务文档或表格。云端现有运行结果是不可变执行证据，只提供原始结果展示/报告下载，以及 `useful`、`needs_improvement` 两类反馈和由差评创建验收样例的动作。新版反馈区不把“符合预期”评价冒充为正式报告验收，也不在浏览器中覆盖运行原始结果。

- 需要：报告修订契约与读取 query，区分原始运行结果、当前人工修订版、修订人、修订时间及修订号；原始结果始终可追溯且不被覆盖。
- 需要：按字段提交修订的 Server Action，携带期望修订号进行并发控制、敏感信息校验和操作审计；修订后原先的人工验收失效。
- 需要：针对确切报告修订号的人工验收动作与状态 query，明确验收人和时间；不能把现有运行反馈的 `useful` 值当作这一证据。
- 需要：若继续提供业务文档/表格导出，由服务端按所选修订号生成经过脱敏的文件，明确格式、字段映射和导出记录；当前下载的运行报告不能冒充旧版修订版导出。

## 15. 手动运行请求的精确核对

试运行写动作支持客户端请求标识，可避免同一请求在网络中断后被重复创建；但目前没有按该标识读取运行结果的 query。现有启动服务在检查当前正式版本与输入后才查找重复请求，且重复标识没有与原输入摘要做冲突校验。前端因此在响应不确定时锁住原输入、沿用原请求标识重试，并提供同一助手的运行记录入口；页面刷新或正式版本在核对前变化时，仍不能精确定位上次请求。

- 需要：按工作区、助手和客户端请求标识精确查询手动运行的状态、编号和原输入摘要，返回已创建、明确失败或尚未收到三种可区分结果；不能只依赖最近运行列表猜测。
- 需要：幂等检查先于当前正式版本和新输入的预检；同一标识若携带不同输入或助手，应返回明确冲突，而不是静默返回旧运行。
- 需要：明确服务端保留请求标识的期限，以及网络断开后跨标签页或刷新时的安全核对规则。

## 16. 验收样例创建与整轮验收的精确核对

当前创建样例动作会对同一助手下名称、输入和结果检查完全一致的启用样例去重；更新样例带修订时间，归档/恢复可重复提交。前端在响应丢失后可于同一标签页重用原提交快照，但刷新后无法精确确认首次请求。整轮验收虽可传客户端请求标识，验收总览与助手详情现可在同一标签页沿用原标识核对；仍缺少按该标识读取结果的 query，不能把最近一轮记录当成精确证明。

- 需要：创建样例支持客户端请求标识并返回样例编号；服务端保存标识与输入摘要，重复标识配不同内容必须返回冲突，不能创建另一条样例。
- 需要：按工作区、助手和请求标识查询样例创建结果，明确区分已创建、明确拒绝与未收到，并返回脱敏后的样例摘要及归档状态；不能只靠当前页列表名称推测。
- 需要：按整轮验收请求标识读取验收编号、绑定版本、运行状态及逐项结果，使响应丢失或跨刷新后可以精确定位上次验收，不依赖“最近一轮”猜测。
- 写动作结果建议区分确定失败与提交结果未知；目前通用的 `ok: false` 加文字错误不足以让前端安全判断是否允许修改内容后重新提交。

## 17. 业务节点依据的重新校准

旧版 V5.7 会为每个业务节点展示真实需求证据、输入来源、业务规则、产出和可观察完成标准，并在修改节点或工具绑定后重新溯源。云端草稿的 `businessSpec` 已保存这些设计时信息，当前前端据实展示；但现有保存草稿、设计审计、安全修复和发布动作没有在节点编辑后重新生成业务依据与来源检查。旧状态可能过期，因此界面将其表述为“草稿记录”，不宣称是实时可执行证明。

- 需要：以草稿修订号为基线的重新业务溯源动作，输入当前需求、流程、输入/输出契约、资料与工具绑定，返回逐节点更新后的 `businessSpec`、缺失来源、需求覆盖和可观察完成标准；应在服务端裁定，不由浏览器根据节点标题推测。
- 需要：保存草稿或发布前的服务端校验能够识别与当前节点内容不一致的旧 `businessSpec`，给出可定位到节点的阻塞原因；发布不应仅凭历史 `grounding.status` 或 `executability.status` 放行。
- 需要：若支持人工修改业务依据，提供带修订号的节点规格更新动作及证据来源契约，并记录修改人和时间；不能把自由填写的“依据”直接等同于已核验的用户需求。

## 18. 验收失败定位与修复建议

旧版 V5.7 在验收失败后可查看关联流程节点、生成修复方案、确认应用并重新验收。云端设计审计已经能提供真实的 `nodeId`，本次前端据此实现问题到流程节点的定位；但自动验收的逐项结果目前只有样例、状态、错误和运行编号，不能可靠判断是哪一个节点造成失败，也没有可执行的修复方案契约。界面不能把样例失败直接归因到某个节点，或在浏览器中伪造“一键修复”。

- 需要：逐项验收结果的服务端诊断 query，绑定验收编号、样例、版本和真实运行证据，返回可为空的关联节点编号、失败阶段、可读原因与证据引用；不能仅凭报错文本或当前草稿图推断节点。
- 需要：基于指定版本与失败证据生成修复建议的 action/query，返回结构化、可预览的流程差异、影响的样例和风险说明，并标明方案是否仍适用于当前草稿修订号。
- 需要：经用户确认后应用修复的 Server Action，使用草稿修订号与幂等请求标识，保留原版本及变更审计；并提供针对修复后候选版本重新验收的明确入口。不得由前端直接改写历史验收结论或运行证据。

## 19. 助手目录的业务状态摘要

旧版目录按助手展示正式版本、候选版本、等待人工、失败任务、完成任务与成功率。云端 `AgentSummary` 目前只返回名称、说明、状态文字、版本总数和更新时间，无法据此可靠判断“正式运行”“需要关注”或最近结果；前端没有把版本总数或当前页运行数伪装成这些业务状态。

- 需要：与助手列表同一工作区权限和搜索/分页口径的批量目录摘要 query，返回每位助手的正式版本编号与发布时间、候选版本编号、待人工确认/待外部事件/失败/已完成运行数、最近运行状态与时间；所有数量须由服务端按全量记录聚合，明确是否包含归档和取消的运行。
- 需要：工作区级独立助手、AI 团队、拥有正式版本、需要关注的总数，不能由当前 20 条分页记录推算；独立/团队分类还依赖第 11 节所述持久类型契约。
- 需要：若展示成功率，服务端须定义统计窗口、分母、取消与重试的计算方式，并返回样本量；“存在正式版本”不等于当前健康或正在运行，目录标签不得由前端自行推断。

## 20. 按助手发布版本预览资料检索

现有 `searchKnowledgeChunks` 查询工作区当前全部已就绪资料，只能作为资料库检索预览。正式运行的知识步骤会按发布时冻结的 `knowledgeSnapshot`、节点选定来源和节点检索词执行，结果可能与全库预览不同。前端已明确标注这一边界，不将全库命中承诺为任一助手运行时的命中。

- 需要：只读的版本/节点范围检索预览 query，输入工作区权限下的助手、已发布版本、知识节点和可选试用输入；服务端从对应版本的资料快照与节点配置确定真实资料范围和检索词，并返回实际使用的来源摘要、命中段落、扫描上限及截断状态。
- 需要：预览结果明确绑定版本和节点修订；版本变化、资料归档或解析状态变化后应提示结果已过期。不能让前端用全库检索结果过滤后冒充正式运行范围，也不能凭当前草稿推断历史发布版本。

## 21. Web Tool 的定义、发布与调用证据

旧版 `WebToolPublisher` 提供工具定义保存与编辑、发布/停用、调用密钥轮换和运行诊断；云端版目前没有 Web Tool 的共享契约、工作区查询、写动作或调用 Route Handler。`/web-tools` 已能读取真实正式版本、核对输入/交付契约，并在浏览器内预览输入布局与检查试填格式；这些只作发布前准备，不保存试填、不执行助手、不创建工具或模拟结果。现有运行报告导出与服务端工具注册表不是对外发布的 Web Tool。前端不能生成看似可调用的地址、密钥或“已发布”状态。

- 需要：`WebToolDefinition`、`WebToolInput`、`WebToolPublication`、`WebToolInvocationSummary` 等 Zod 契约，明确工具名称、用途、关联助手及固定发布版本、输入/输出 schema、鉴权方式、发布修订号、状态与调用范围；面向员工的读取视图只能返回密钥提示，不能返回密钥原文。
- 需要：工作区内工具定义列表/详情与默认建议配置 query；创建、修改、发布、停用、删除/归档的 Server Action。所有写动作校验助手版本、输入契约、调用权限和并发修订号，并留下审计记录。版本变更不能悄悄改变已发布工具的调用语义。
- 需要：首次生成与轮换密钥的动作，只在生成当次返回一次明文；旧密钥失效窗口、泄露处置和幂等请求标识由服务端定义。前端不得自行生成或保存可用密钥。
- 需要：真正的调用 Route Handler，执行鉴权、输入校验、速率/预算限制，复用既有运行创建与 Workflow 执行链路，并返回可追踪的调用/运行编号及符合契约的结果或错误。发布动作在该路径可用之前不得返回“已发布”。
- 需要：按工具分页查询调用记录、成功/失败、耗时和脱敏错误，支持定位到真实运行。旧版运行诊断和密钥轮换确认弹窗需基于这些服务端结果，而非前端计数。

## 22. MCP 连接、发现与授权

旧版资源中心支持 MCP 连接保存、握手测试、工具发现及授权；云端 `TOOL_REGISTRY_JSON` 只注册服务端 `http-json` 工具，不是 MCP 客户端，也没有持久化的 MCP 连接实例。`/connections` 已将实际登记的工具与无法读取的连接实例分开说明；当前工具目录仅展示现有注册项，不声称 MCP 可连接或可运行。

- 需要：`McpConnectionInput`、`McpConnectionView`、`McpDiscoveredTool`、`McpToolGrant` 等 Zod 契约，区分连接草稿、握手成功、发现结果、授权及生效配置修订号；读取视图只返回掩码后的认证信息与测试时间。
- 需要：工作区 MCP 连接列表/详情、保存/更新/停用动作，以及由服务端执行的握手测试和 `tools/list` 发现动作。连接测试应返回协议版本、服务器标识、能力、延迟和脱敏失败分类，不能仅用浏览器连通性判断成功。
- 需要：发现结果按服务端修订号保存或绑定，明确工具名称、描述、输入 schema、来源连接、风险级别和最近验证时间；连接配置变化时，旧发现与授权自动失效或显式待复核。
- 需要：逐工具、逐助手/版本的授权读取和写动作，带修订号、审批规则和审计记录。画布选择工具、发布门槛和运行时都应由服务端检验授权，不由前端开关替代。
- 需要：MCP 执行适配层在服务端维护会话、超时、取消、错误分类及凭据隔离，将调用证据写入现有运行轨迹；未具备该执行路径前，目录不能把发现到的 MCP 工具标为可执行。
